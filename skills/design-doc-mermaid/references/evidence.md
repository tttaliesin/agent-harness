# Source evidence and review

For a diagram explaining existing code, inspect the scoped entrypoints, configuration, actual call sites, transport and state transitions.
Do not checkout or discard unrelated working-tree edits to inspect a baseline; use revision-specific reads.
Record stable node/edge identifiers independently of display labels.

| Element | Claim | Evidence | Status |
| --- | --- | --- | --- |
| Actual node or edge ID | What it represents | Repository revision and path/line, user fact, or observation | Observed, inferred, proposed, or unknown |

Do not equate source existence with semantic support: read the cited lines and verify the claimed relationship.
Static declarations do not demonstrate deployed topology, network reachability or physical execution.
Keep inferred links visibly distinct; do not invent services, resource counts, ports or retries.
For proposed designs, label choices as proposed and retain unresolved requirements instead of requiring nonexistent code evidence.

Templates and framework examples are illustrations only.
Unchecked security/test/review items stay unverified until actual evidence supports them.
Do not mark team approval complete because a template contains a review section.
Require team/user review before integration only when the user or repository explicitly requires it.
Complete source preparation and available validation first; reuse matching approval and pause only the action subject to an unmet requirement.
